## 리뷰

### 1. 사용 흐름 (User Journey) 분석 및 누락/병목 단계

#### 1.1 학부모 사용 흐름: 최초 진입부터 첫 채팅 발송까지
1. **[화면 1: 랜딩 및 프로필 탐색 (홈)]**:
   - 상단 필터 바(동·과목·학년) + 하단 프로필 카드 그리드/피드.
   - **중요 결정사항 (Guest 탐색 허용)**: 전봇대 전단지의 최대 장점은 '누구나 즉시 둘러볼 수 있다'는 점이다. 따라서 **비로그인 상태에서도 프로필 검색 및 상세 열람은 100% 가능**해야 한다. 가입을 강제하면 진입 장벽으로 인해 첫 화면 이탈률이 급증한다.
2. **[화면 2: 프로필 상세 뷰]**:
   - 선생님 상세 정보(학력 배지, 신고 유형, 교습비, 과목, 수업 가능 동, 출신 고교, 소개글) 확인.
   - 하단 고정 CTA 버튼: `문의하기` (또는 `채팅 시작하기`).
3. **[화면 3: 가입/로그인 유도 (바텀시트 or 모달)]**:
   - 비로그인 상태에서 `문의하기` 클릭 시 가입/로그인 모달 노출.
   - 역할 선택('학부모') + 만 14세 이상 체크 + 간편 로그인(카카오 or 이메일).
4. **[화면 4: 첫 문의 메시지 작성 및 발송]**:
   - 빈 채팅방으로 바로 던져지면 학부모가 무엇을 써야 할지 막막하여 이탈하기 쉽다 (**빠진 단계**).
   - 첫 문의 시 **'기본 질문 템플릿'**(예: 학생 학년, 희망 요일/시간대, 현재 등급이나 고민 등)을 선택형 칩이나 플레이스홀더로 제공해야 전환율이 보장된다.
5. **[화면 5: 채팅방 및 알림 수신]**:
   - 메시지 발송 후 대화방 유지.
   - **치명적 병목 (빠진 단계)**: 선생님이 답장했을 때 학부모가 웹 브라우저를 닫은 상태라면 답장을 인지할 방법이 없다. 최소한 '선생님이 첫 답장을 보냈을 때 등록된 연락처(이메일 or 카카오 알림톡)로 안내'가 없으면 연결이 성립되지 않는다.

#### 1.2 선생님 사용 흐름: 가입부터 프로필 검색 노출 및 첫 응답까지
1. **[화면 1: 회원가입 및 역할 선택]**:
   - '선생님으로 시작하기' 선택 + 만 14세 이상 확인 + 계정 생성.
2. **[화면 2: 프로필 작성 (온보딩)]**:
   - 필수 정보(이름, 과목, 학년, 동, 교습비, 신고 유형, 대학·학과) 및 선택 정보(출신 고교, 소개) 입력.
   - **빠진 단계 (저장 상태 구분)**: 작성 도중 이탈을 고려한 `임시저장` 및 `공개/숨김` 상태 전환 토글 명시 필요. 작성 완료 즉시 '공개' 상태로 검색에 노출되는 흐름이어야 함.
3. **[화면 3: 대학 이메일 인증 (선택/권장)]**:
   - 프로필 작성 직후 또는 마이페이지에서 `ac.kr` 이메일 입력 -> 6자리 인증코드 검증 -> `재학 인증` 배지 부여.
   - *의문점*: 일반 교습자(졸업생/전문강사)는 이메일 인증을 못 하는데, 이 경우 검수 대기 없이 바로 '미인증' 상태로 검색 노출이 되는지 정책 확정 필요 (MVP에서는 즉시 노출 + 미인증 마크가 적절).
4. **[화면 4: 학부모 채팅 수신 및 응답]**:
   - **치명적 병목 (빠진 단계)**: 학부모가 첫 메시지를 보냈을 때 선생님이 서비스에 접속해 있지 않으면 메시지가 방치된다. 선생님에게 즉각적인 수신 통보(이메일 or 알림톡)가 가야 한다.

### 2. 시장 조사(T-041)와의 정합성 검토

1. **시사점과 잘 부합하는 점**:
   - **수수료 0원 / 결제 배제**: 김과외(첫 달 25% 수수료 논란)나 숨고(열람 시 캐시 차감)의 피로도를 제거하고, 중개 수수료 없는 순수 리드 연결 모델을 채택한 점은 초기 공급자(선생님) 확보에 결정적으로 유리함.
   - **전단지의 1페이지 프로필 카드화**: 핵심 정보만 한 화면에 압축해 보여주는 방향성 적합.
2. **어긋나거나 빠진 핵심 요소**:
   - **전단지 감성의 '프로필 보관/찜하기' 인터랙션 누락 (market §4.3)**:
     - 시장 조사에서 전봇대 전단지의 핵심 행동 패턴은 "전화번호 탭을 뜯어서 주머니에 보관했다가 여러 명을 비교하는 것"으로 분석됨.
     - 초안에는 '찜하기/보관함'이 아예 없고 오직 '채팅 시작'만 있음. 학부모는 바로 채팅하기 전 2~3명의 선생님 프로필을 찜해두고 비교하고 싶어 하므로, 가벼운 '북마크/찜' 기능이 필요함.
   - **교습비 '숫자 필수' 표기의 단가 기준 모호성 (학원법 준수 vs 현장 괴리)**:
     - 전단지에는 100% "상담 후 협의"로 적히지만, 학원법 제15조 광고 규정 준수를 위해 숫자 입력을 강제한 방향은 규제상 불가피함.
     - 그러나 단순히 `숫자(원) + 회당/월`로만 두면, 주 1회 1시간인지 주 2회 2시간인지 기준이 없어 선생님이 1만 원 같은 허수 금액을 적고 채팅에서 말을 바꾸는 부작용 발생. **'시간당 단가(시급)'** 또는 **'월 기준(주 N회, 회당 N시간)'**의 명확한 단가 기준 가이드가 폼에 포함되어야 함.
   - **'선배 튜터' 차별점에 대한 검색 지원 누락**:
     - F2에 출신 고교를 적게 해놓고, 정작 F4 검색에는 "동·과목·학년"만 있고 "출신 고교" 검색 필터가 빠져 있음. 수성구 특화 차별점을 살리려면 검색 필터 또는 프로필 카드 내 고교 태그 클릭 시 모아보기 기능이 필수적임.

### 3. 프로필 항목 및 검색 필터 설계안 (수성구 23개 행정동 포함)

#### 3.1 과목 및 학년 목록 세분화안
* **과목 (체크박스 복수 선택)**:
  - 수학: 초등수학 / 중등수학 / 고등수학(공통) / 수1·수2 / 미적분 / 기하 / 확률과통계
  - 영어: 초등영어 / 중등내신 / 고등내신 / 수능영어 / 공인영어(토플·텝스)
  - 국어: 초등국어·논술 / 중등국어 / 고등내신 / 수능국어(문학·독서·언매·화작)
  - 과학: 중등과학 / 통합과학 / 물리학 / 화학 / 생명과학 / 지구과학

  - 초등: 초등 1~3학년 / 초등 4~6학년
  - 중등: 중1 / 중2 / 중3
  - 고등: 고1 / 고2 / 고3 / N수생(성인)

| 생활권역 | 행정동 목록 (총 23개동) | 비고 및 주요 학원/주거 특성 |

### 4. 프론트엔드 스택 제안 (반응형 웹 우선, 앱 확장 및 E2E 테스트)

모바일 뷰포트(360~430px)를 최우선으로 지원하는 모바일 퍼스트 반응형 웹을 전제로 3가지 안을 비교한다.

| 비교 항목 | **1안: Vite + React (TypeScript) + Tailwind CSS** *(강력 추천)* | **2안: Next.js (App Router, TS) + Tailwind CSS** | **3안: Thymeleaf + HTMX + Tailwind** |
| :--- | :--- | :--- | :--- |
| **아키텍처** | 순수 CSR SPA (Single Page Application) | 풀스택 SSR / 하이브리드 웹 | 서버 사이드 모놀리스 렌더링 |
| **배포 및 통합** | - 빌드 결과물(`dist/`)을 Spring Boot 정적 리소스(`static/`)에 단일 번들링 가능.<br>- 서버 1대(Spring Boot)로 완결. | - Node.js 런타임 서버가 별도 필요 (서버 2대 운용 부담).<br>- 정적 익스포트(`output: 'export'`) 시 Next.js 이점 반감. | Spring Boot 단일 프로세스에서 HTML 서빙. Node/npm 환경 불필요. |
| **모바일 UI 생산성** | - Tailwind CSS + shadcn/ui 기반의 고품질 모바일 UI(바텀시트, 드로어, 칩 필터) 즉시 활용 가능. | 1안과 동일하게 React 생태계 UI 컴포넌트 풀 활용 가능. | 순수 HTML/JS로 모바일 모달, 동적 칩 필터링 구현 시 작업 공수 증가. |
| **추후 앱 확장** | **최상**: `Capacitor`를 붙여 동일한 웹 자산을 즉시 iOS/Android 웹뷰 앱으로 패키징 가능. | Capacitor 연동 가능하나 SSR 구조와 충돌 방지를 위해 추가 설정 필요. | 앱 전환 불가 (앱 제작 시 REST API 및 프론트엔드 전면 재구축 필요). |
| **E2E 테스트 연계** | **Playwright (TypeScript)** 활용:<br>- 모바일 디바이스 뷰포트(iPhone, Pixel) 에뮬레이션 완벽 지원.<br>- Spring Boot `@SpringBootTest` 구동 후 Playwright CLI로 E2E 검증 가능. | Playwright 동일 적용 가능. | Playwright 또는 HtmlUnit 적용 가능. |
| **평가** | **MVP에 가장 적합**: 백엔드(Spring)와 완벽히 분리되면서도 배포는 단일 JAR로 묶을 수 있고, 나중에 앱으로 넘어가기 가장 쉬움. | 초기 인프라 오버엔지니어링 우려. | YAGNI에는 맞으나 추후 앱 전환 시 재작업 비용이 큼. |

#### E2E 테스트 방식 구체안 (Playwright + Spring Boot)
- **구조**: `src/e2e/` 디렉토리에 Playwright 테스트 스크립트 작성.
- **테스트 시나리오**:
  1. `선생님 가입 -> 프로필 입력 (범어4동, 수학, 고1) -> 이메일 인증 -> 검색 목록 노출 확인`
  2. `학부모 진입 -> 범어4동 + 수학 필터링 -> 프로필 카드 클릭 -> 로그인 모달 확인 -> 가입 후 첫 채팅 메시지 전송`
  3. `선생님 화면에서 수신 메시지 확인 및 답장 -> 학부모 화면에서 수신 확인`
- **테스트 하네스 통합**: `scripts/verify.sh`의 `full` 검사 단계에서 Spring Boot를 테스트 프로파일로 띄우고 `npx playwright test`를 헤드리스 모드로 실행하여 바이트 검증 및 CI 무결성 유지.

### 5. 우선순위별 검토 의견 및 조치 권고 (P0 / P1 / P2)

#### [P0: 이대로면 서비스 불능 또는 치명적 결함]
1. **메시지 수신 알림(Notification) 부재**:
   - 웹 기반 서비스 특성상 양 당사자가 브라우저를 닫고 있으면 대화가 완전히 단절됨. 학부모의 첫 문의 시 선생님에게, 선생님 답장 시 학부모에게 최소한의 **이메일(가입 이메일) 또는 카카오 알림톡/SMS 발송 트리거**가 MVP에 필수적으로 정의되어야 함.
2. **비로그인 둘러보기(Guest 탐색) 보장**:
   - 가입해야만 검색 목록을 볼 수 있는지 명세에 명확한 언급이 없음. 전단지처럼 '비로그인 사용자에게 검색/상세 열람 100% 개방', '문의하기 클릭 시 로그인' 흐름을 명세 F1/F4에 못박아야 함.
3. **교습비 단가 기준의 구체화**:
   - 학원법 제15조 광고 표시 준수를 위해 숫자를 필수로 하되, `시간당(시급)` 또는 `주 2회 월 8회(회당 2시간)` 등 명확한 교습 시간 기준을 단위로 명시하여 1만 원 적어놓고 채팅에서 올리는 어뷰징 방지.

#### [P1: 차별점 및 사용자 경험 핵심 결함]
1. **수성구 출신 고교 검색/필터 추가**:
   - F2에 출신 고교 입력 필드가 있으므로, F4 검색 조건에도 고교 선택/검색 필터를 추가하거나 프로필 카드의 고교 태그를 클릭하면 해당 학교 출신 선생님만 모아보는 기능 추가 필요.
2. **전단지 감성의 '프로필 보관(찜하기)' 기능 추가**:
   - 학부모가 여러 전단지를 뜯어 보관하듯, 프로필 카드에서 하트/북마크를 누르면 '내가 찜한 선생님' 목록에 보관되는 경량 찜 기능 필요.
3. **첫 문의 템플릿(질문 가이드) 제공**:
   - 학부모의 첫 메시지 입력 부담을 덜어주기 위해 학년, 과목, 수업 희망 시간 등을 쉽게 채울 수 있는 칩/템플릿 폼 제공.
4. **일반 교습자(졸업생/개인과외교습자)의 검색 노출 기준 명확화**:
   - 대학 이메일 인증을 받지 못하는 졸업생/일반 신고자의 프로필이 검수 없이 즉시 노출되는지, '미인증' 배지가 검색 결과에서 불리하게 작용하지 않도록 하는 가이드라인 필요.

#### [P2: 개선 권장 사항]
1. **행정동 4대 권역 그룹핑 UI**: 23개 행정동을 평면 선택하게 하지 않고, 범어/만촌황금/수성중동/지산범물고산 등 생활권역별로 묶어 선택 피로도 감소.
2. **로그인 수단 결정**: 학부모의 모바일 접근성을 위해 '카카오 간편 로그인'을 1순위로 채택할 것을 권장.
3. **차단/신고 접수 피드백**: 신고 접수 시 "운영팀에 접수되었습니다" 토스트 알림 및 차단 시 대화방 비활성화 UI 처리.
