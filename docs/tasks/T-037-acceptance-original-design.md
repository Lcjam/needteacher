## 결과

- 생성만 허용하는 guard 예외는 권하지 않는다. 파일 존재 검사와 실제 셸 쓰기 사이 경합, 삭제 후 재생성, 경로 없는 `git clean`·`git reset --hard`, 우회 경로 때문에 원본 고정을 보장하지 못한다.
- 기존 `.harness-unlock` 절차를 사용한다: Codex가 일반 테스트 경로에서 red 원본을 작성·확인하고, 사용자 잠금 해제 중 오케스트레이터가 보호된 `src/acceptance/java`로 옮긴 뒤 잠금을 닫는다. 새 guard 예외가 필요 없다.
- 원본 전용 PR은 대응 실행 테스트가 없어도 green이어야 한다. 병합된 원본이 있는 다음 일반 PR부터 CI가 대응 파일 존재·바이트 일치를 강제한다. 상세 판정과 오류 문구는 아래 명세.
- 원본은 병합 후 유지한다. 요구 변경·폐기는 별도 원본 전용 PR과 코드오너 승인으로 먼저 확정하고, 다음 구현 PR에서 실행 테스트를 맞춘다.
- 검증: `guard.py`·`verify.sh`·CODEOWNERS·T-036 범위 대조(설계만, 실행 없음). 바꾼 파일은 이 카드만. 남은 일: 다음 카드에서 게이트·회귀 검사 구현.
- 결론: 승인·병합된 원본이 있는 기능은 아래 CI 규칙으로 T-031·T-033의 테스트 변조 P0을 닫는다. 원본 없는 기능의 요구 충실도와 승인 전 원본 내용은 사람 리뷰에 남는다.

## 명세

### 로컬 및 PR 흐름

0. 첫 원본 PR 전에 검증 코드와 `/backend/src/acceptance/java/ @Lcjam` CODEOWNERS 규칙을 별도 하네스 변경으로 병합하고, ruleset의 코드오너 승인을 켠다. 원본 전용 PR에 이 보호 설정 변경을 섞지 않는다.
1. 새 인수 테스트는 Codex가 `backend/src/test/java/<상대경로>.java`에 작성하고 직접 red를 확인한다. 오케스트레이터만 커밋한다. 원본 전용 카드에는 임시 테스트 경로와 원본 경로를 모두 scope로 적는다.
2. 사용자가 `.harness-unlock`을 만든 동안 오케스트레이터가 파일을 `backend/src/acceptance/java/<같은 상대경로>.java`로 **이동**하고 테스트 경로가 비었는지 확인한다. 사용자가 잠금을 제거한 뒤 원본과 카드만 커밋한다. 원본 폴더는 Gradle 소스셋에 포함하지 않는다.
3. 원본 전용 PR은 사용자가 코드오너로 내용을 검토·승인해 `main`에 병합한다. 이 PR에는 운영 코드나 실행 테스트를 넣지 않는다. 다음 일반 PR이 이 원본을 실행 테스트로 활성화하므로, 원본 대기 중에는 다른 일반 PR을 병합하지 않는다.
4. 구현 담당은 병합된 원본을 `src/test/java` 같은 상대경로로 그대로 복사하고 운영 코드를 작성한다. Codex는 복사본 일치, red→green, full 결과와 요구 경계값을 리뷰한다. 새 테스트 파일을 원본 없이 넣는 일반 PR은 CI가 거부한다.
5. 원본은 감사 기준으로 계속 둔다. 요구 변경 시 원본만 바꾸는 별도 PR을 먼저 승인·병합하고 다음 일반 PR에서 실행 테스트를 동기화한다. 원본 폐기는 원본 경로를 `quality/test-removals.txt`에 같은 변경으로 등록하고 별도 코드오너 PR에서 삭제한다. 실행 테스트 변경·삭제도 해당 경로를 등록한다.

### `verify.sh` 판정

- 모든 경로와 내용은 고정한 `$tree` 및 `$base`에서 읽는다. 원본 경로 `backend/src/acceptance/java/<rel>`은 실행 경로 `backend/src/test/java/<rel>`에 일대일 대응한다. 원본·실행 파일은 Git 일반 파일(`100644`)이어야 하며 심볼릭 링크와 비 `.java` 원본은 실패한다.
- **원본 전용**은 `$base..$tree` 변경이 원본 폴더, 해당 작업 카드, 필요 시 `quality/test-removals.txt`뿐이고 원본 변경이 실제로 있을 때만 인정한다. 이 경우 대응 실행 파일의 부재·불일치를 잠시 허용한다. 원본 신규와 운영 코드·실행 테스트를 같은 PR에 넣으면 `원본은 별도 PR로 먼저 승인·병합`으로 실패한다.
- **일반 변경**에서는 `$base`에 있던 모든 원본의 대응 실행 파일이 `$tree`에 존재하고 `cmp -s`로 완전히 같아야 한다. 원본이 현재 tree에서 수정·삭제됐으면 `원본 변경은 별도 코드오너 PR`으로 실패한다. 대응 파일 누락은 `인수 테스트 누락: <경로>`, 불일치는 `인수 테스트 원본 불일치: <경로>`로 실패한다.
- 일반 변경에서 새로 추가한 `src/test/java/**/*Test.java`·`*IT.java`도 같은 상대경로의 원본이 `$base`에 없으면 `인수 테스트 원본 없음: <경로>`로 실패한다. 초기 하네스 첫 커밋(빈 base)의 기존 테스트만 명시적으로 이 규칙에서 제외한다. 등록 예외는 이번 diff에서 `quality/test-removals.txt`에 해당 **실행 테스트 경로**를 추가한 경우에만 허용하고 코드오너 리뷰를 받는다.
- 원본 전용 PR 병합 직후의 `main` push도 같은 diff 분류로 통과한다. 다음 일반 PR은 대기 중인 모든 원본을 활성화해야 하므로 여러 기능의 원본을 쌓아 두지 않는다. 전체 검사는 비싼 Gradle 빌드 전에 실행한다.

### `test_verify.sh` 사례

- 원본만 추가하고 실행 테스트 없음 → 통과; 원본+운영 코드 또는 실행 테스트를 함께 추가 → 실패.
- 다음 변경에서 원본 그대로 복사 → 통과; 복사본 누락·한 글자 변경·조기 `return` 추가 → 각각 실패; 정확한 경로를 같은 변경의 `test-removals.txt`에 등록 → 허용.
- 일반 변경에서 원본 없는 새 `*Test`·`*IT` → 실패; 원본 수정·삭제 동시 구현 → 실패; 원본 전용 수정·등록한 폐기 → 통과.
- 원본 심볼릭 링크·비 Java 파일 → 실패; 다른 상대경로·대소문자 충돌 → 실패; 원본 대기 중의 무관한 일반 PR → 대응 테스트가 없으면 실패.
