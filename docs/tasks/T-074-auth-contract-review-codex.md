## 목표

`docs/tasks/T-073-auth-acceptance.md`의 계약 v1을 리뷰한다. 이 계약으로 네가 인수 테스트를 쓰게 되므로 **테스트로 정확히 고정할 수 있는가**와 **보안 구멍**을 본다. 코드는 쓰지 않는다. agy가 같은 계약을 따로 리뷰한다(T-075). 그 카드는 읽지 않는다.

## 볼 것

1. **테스트 가능성:** 표·규칙마다 "어떤 요청 → 어떤 단언"이 하나로 정해지는가. 모호하거나 두 가지로 읽히는 문장, 시간 경계·순서에 따라 결과가 흔들릴 문장(예: 테스트 간 발송 기록·시계 공유)을 찾는다.
2. **보안:** 계정 열거, 코드 대입(재요청 우회 포함), 세션 고정, 로그인 CSRF, 탈퇴 후 남은 세션. 계약이 막지 못하는 경로가 있으면 최소 수정안.
3. **오케스트레이터가 확신 없는 곳:**
   - 탈퇴한 계정의 다른 세션 거부(`### 탈퇴` 3번째 줄). 슬라이스 1 원본은 계정 행 없는 `user()`로 쓰기를 하므로 "계정 행이 있어야 인증"은 못 쓴다. 이 계약을 구현자가 슬라이스 1을 깨지 않고 만족시킬 수 있나.
   - 만료 코드 삭제를 `email_codes`/`email` 이름으로 DB에서 관찰하는 것(T-072 1번 후속). 결합이 과한가, 더 나은 관찰 방법이 있나.
   - 익명 로그아웃 `204`(멱등) — T-072 5번은 "익명 거부"를 말했는데 이렇게 바꿨다. 동의하나.
4. **빠진 것:** T-072 6번 목록 중 계약에 안 들어간 것.

## 리뷰

**판정: 고쳐서 확정.** 아래 P0을 반영하고, 특히 만료 코드 삭제의 의미를 `mvp.md`와 일치시킨 뒤 원본을 작성한다.

1. **P0 — 만료 즉시 삭제와 1분 주기 삭제가 충돌한다.** `mvp.md`는 “만료 즉시 삭제”로 확정했는데, 계약의 다음 요청/1분 정리는 최대 1분 동안 만료 행을 남긴다(`docs/proposals/mvp.md:128-131`, `docs/tasks/T-073-auth-acceptance.md:60-65`). **교체 문장:** “코드는 발급 10분 정각부터 검증 불가다. 저장 행은 만료 후 최대 60초 이내에 삭제한다.” 이 완화안을 택한다면 사용자 결정이 담긴 `mvp.md`도 함께 변경해야 한다. 원래 뜻이 물리적 정각 삭제라면 정리 트리거와 허용 오차부터 다시 정해야 하므로 현 문구로 원본을 고정하면 안 된다.

2. **P0 — 코드 대입·재요청의 카운터 범위와 동시성 미정.** 계약에는 코드당 5회, 이메일당 발송 간격/24시간 한도는 있지만 세션을 바꾸거나 같은 이메일 표기를 바꿀 때 카운터가 공유되는지와 동시 검증의 1회 사용 보장이 없다(`docs/tasks/T-073-auth-acceptance.md:50-58`). **교체 문장:** “정규화된 이메일의 발송 기록은 모든 세션에서 공유한다. 실패 횟수는 코드 발급 건별로 모든 세션에서 원자적으로 누적하고, 5회 실패 후에는 어느 세션의 정답도 거부한다. 성공 소비도 원자적이어서 동시 확인에서 최대 한 요청만 성공한다. `429` 요청은 기존 코드·발송 기록을 바꾸지 않는다.” 신규 IT는 쿠키 저장소 두 개로 실패 횟수를 나눠 입력하고, 정답·재전송을 교차 확인한다.

3. **P0 — `SIGNUP_REQUIRED` 뒤 옛 세션의 `GET /me = 401`은 세션 고정 방지를 검증하지 못한다.** 가입 전 세션은 ID가 그대로여도 원래 `/me`가 `401`이다(`docs/tasks/T-073-auth-acceptance.md:29-30,43`). **교체 문장:** “확인 성공으로 ID를 바꾼 뒤, 옛 `SESSION` 쿠키와 유효한 CSRF 토큰으로 `POST /api/v1/auth/signup`을 보내면 `401`이고, 새 쿠키만 가입할 수 있다. `SIGNUP_REQUIRED`에서도 새 CSRF 토큰을 발급해 이전 토큰의 POST를 `403`으로 거부한다.” 기존 로그인/가입의 토큰 교체 단언은 유지한다(`docs/tasks/T-073-auth-acceptance.md:44`).

4. **P0 — 확인된 이메일의 보관 수명·재사용이 빠졌다.** 코드의 10분 제한만 있고 확인 후 가입 자격의 만료·소비가 정해지지 않아, 오래된 익명 세션이나 다른 이메일 재확인 뒤에도 가입이 열릴 수 있다(`docs/tasks/T-073-auth-acceptance.md:29-30,52,55`). **교체 문장:** “`SIGNUP_REQUIRED`의 확인된 이메일은 새 세션 ID에만 묶고 확인 시각부터 10분 미만 동안 한 번만 가입에 쓸 수 있다. 다른 이메일을 확인하면 이전 확인 상태를 버린다. 로그아웃·가입 성공·만료 후에는 재사용할 수 없다.” 시계 경계와 다른 이메일 재확인을 HTTP로 단언한다.

5. **P1 — 탈퇴한 계정의 다른 세션 거부는 가능하지만 검사 대상을 제한해야 한다.** 전체 `Authentication`에 계정 행 존재 검사를 걸면 계정 없이 `user()`를 쓰는 슬라이스 1 원본이 깨진다(`docs/tasks/T-073-auth-acceptance.md:22,69-72`, `docs/tasks/T-045-tutor-profile-acceptance.md:20`, `docs/proposals/mvp.md:167-168`). **교체 문장:** “실제 이메일 로그인으로 만든 세션에는 계정 ID를 결속한다. 탈퇴 시 그 ID의 모든 실제 로그인 세션을 무효화하거나 다음 요청에서 철회 상태를 확인해 `401`로 거부한다. 계정 행 없이 주입한 테스트 주체의 인증 규칙은 바꾸지 않는다.” 두 실제 세션 생성은 첫 로그인 후 60초가 지나 새 코드를 받아 둘째 쿠키 저장소에서 확인하는 순서로 명시한다(`docs/tasks/T-073-auth-acceptance.md:57`).

6. **P1 — DB 관찰은 삭제 요구에 한해 허용할 만하나, 현재 단언은 “전부 삭제”를 입증하지 않는다.** HTTP만으로 물리 삭제는 보이지 않으므로 `email_codes(email)`의 읽기 전용 계약은 정당하다. 다만 다른 이메일 하나를 요청한 뒤 이전 이메일 한 행만 검사하면 전역 만료 정리를 증명하지 못한다(`docs/tasks/T-073-auth-acceptance.md:62-65`, `docs/tasks/T-072-slice2-testability-codex.md:37`). **교체 문장:** “원본은 삭제 확인에만 `email_codes.email`을 읽는다. 만료시킨 서로 다른 이메일 A·B의 행을 다음 이메일 C 요청 뒤 각각 0개로 단언하고, 소비·5회 실패 뒤에도 해당 행 0개를 본다. 시각 컬럼이나 코드 값은 DB에서 수정하지 않는다.” 테이블 이름을 아예 숨기는 대안은 물리 삭제를 테스트할 관찰 지점을 없앤다.

7. **P1 — 시간·메일 테스트의 독립성과 24시간 경계가 부족하다.** 60초/10분은 직전·정각이 있지만 24시간의 슬라이딩 구간과 `Retry-After` 값, 거부된 요청의 집계 여부는 미정이다(`docs/tasks/T-073-auth-acceptance.md:52,56-58,81-83`). **교체 문장:** “테스트마다 고유 이메일과 기준 시각을 쓰고, 메일은 그 수신인 앞으로 새로 온 것만 기다린다. 발송 횟수는 현재 시각 직전 24시간의 성공 발송만 센다. 24시간 정각에는 가장 오래된 발송이 구간에서 빠지며, `Retry-After`는 다음 허용 시각까지 남은 초를 올림한 양의 정수다.” 10번째 허용·11번째 거부·첫 발송 24시간 정각 재허용을 단언한다.

8. **P1 — 14일 유휴 만료는 조작 `Clock`으로 HTTP 만료를 앞당길 수 없다.** 계약은 `Clock`으로 코드 시각을 검증하지만 서블릿 세션의 유휴 시계는 별개다(`docs/tasks/T-073-auth-acceptance.md:42,82`). **교체 문장:** “실제 HTTP에서는 로그인 응답의 `SESSION` 쿠키 속성·`Max-Age=1209600`을 확인하고, 세션의 14일 유휴 제한은 적용된 서블릿 세션 설정값으로 단언한다.” 14일을 실제로 기다리는 IT는 두지 않는다.

9. **P2 — 익명 로그아웃 `204`에 동의한다.** 멱등 종료는 기존 세션이 없어도 같은 결과이며, 계약의 전 POST CSRF 규칙이 있으므로 익명 무토큰 요청은 여전히 `403`이다(`docs/tasks/T-073-auth-acceptance.md:31,36`). **교체 문장:** “익명 로그아웃도 유효한 CSRF 토큰이면 `204`이고, 토큰 누락·오류는 `403`; 로그인 상태 로그아웃 뒤 옛 쿠키의 `/me`는 `401`.” T-072의 ‘익명 거부’ 제안은 이 계약으로 대체한다(`docs/tasks/T-072-slice2-testability-codex.md:45`).

10. **P1 — T-072의 6번 중 평문 비저장·나이 자기진술 실패 경계가 단언으로 연결되지 않았다.** 계약은 평문 비저장, `ageOver14=true`를 말하지만 IT 관찰법과 `false`/누락 검증이 없다(`docs/tasks/T-073-auth-acceptance.md:30,62,85`, `docs/tasks/T-072-slice2-testability-codex.md:47`). **교체 문장:** “가입은 `ageOver14` 누락·`false` 각각 `400`이며 계정을 만들지 않는다. 신규 IT는 메일에서 추출한 코드를 저장 행의 문자값 어디에도 평문으로 포함하지 않는지 읽기 전용으로 확인한다.” 이미 들어간 대소문자 단일 계정·5회 실패 뒤 정답 거부·재가입 새 ID는 유지한다(`docs/tasks/T-073-auth-acceptance.md:50,54,72`).
